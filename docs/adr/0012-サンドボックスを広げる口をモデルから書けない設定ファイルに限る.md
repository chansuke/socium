# サンドボックスを広げる口をモデルから書けない設定ファイルに限る

## Context and Problem Statement

サンドボックスはワークスペース、システムの実行環境、private な HOME だけを見せ、方針はコードに固定されていた。そのため crates.io に依存するプロジェクトは `~/.cargo` が見えずにビルドできず、rustup や mise だけで入れた道具は PATH から黙って外れ、コマンドは最長 120 秒で打ち切られた (2026-11-14 のレビュー N5)。誰が、どこまでサンドボックスを広げられるようにするかを決める。所有者は「モデルから書けない `~/.config/socium/` で、読み取り専用マウントと PATH と時間上限を宣言する」と決めた。

## Decision Drivers

* モデルは権限を要求できない、という原則を保つ。
* Rust・Go・Node の標準的な構成で、ビルドとテストがサンドボックスの中で回る。
* 設定の誤りでホームや認証情報を見せない。
* 起動時に、何を足したかが利用者に見える。

## Considered Options

* 固定のまま
* 利用者の設定ファイルで、読み取り専用マウント・PATH・環境変数・時間上限を宣言する
* 承認ダイアログで、その場の権限拡大を許す
* DSH のようにホスト全体を読み取り可にする

## Decision Outcome

Chosen option: 「利用者の設定ファイルで宣言する」。モデルの書いたものが権限を決めない形を保ったまま、所有者が自分の環境に合わせて必要な分だけ広げられる。

* 設定は `$XDG_CONFIG_HOME/socium/config.toml`、なければ `~/.config/socium/config.toml`、または `SOCIUM_CONFIG_FILE` の指すファイル。ワークスペースが設定ディレクトリ、`SOCIUM_CONFIG_FILE`、`SOCIUM_MODELS_FILE`、`SOCIUM_AGENTS_DIR` のどれかを含むなら起動しない。モデルのファイル tool もコマンドも、設定に届かない。
* `[sandbox]` の項目:
  * `read_only`: 読み取り専用でマウントするホストのディレクトリ。`~/` を展開し、実体のパスと、symlink なら書いたパスの両方にマウントする。`/`、ホームとその祖先、`/proc`、`/dev`、`/socium-home`、`/tmp` とその祖先は誤り。存在しないものは警告して飛ばす。マウントは新しい `/tmp` の後、ワークスペースの前に置き、ワークスペースの祖先を挙げてもワークスペースを読み取り専用にしたり `.socium` を見せたりしない。中の実行ファイルは実行できる。
  * `path`: PATH に足すディレクトリ。`read_only` かシステムの実行環境の中にあるものだけ残し、他は警告して飛ばす。bwrap 自体はシステムの PATH からしか探さない。
  * `env`: コマンドに渡す変数。名前は大文字に限り、`PATH`・`HOME`・`TMPDIR`・`GIT_*` は誤り。
  * `command_timeout`: コマンドの最長時間 (秒、1〜86400、既定 120)。モデルはこれより短くは頼めるが長くは頼めず、tool の説明に上限を出す。
* 知らない項目は誤りにする (`deny_unknown_fields`)。ネットワークを開く項目は持たない。
* 起動時に、足したマウントと自動承認の設定を警告欄に出す。

### Consequences

* Good, because `~/.cargo/registry` と `~/.rustup` を見せ、`CARGO_HOME` を渡せば、crates.io に依存するプロジェクトがオフラインでビルドできる。
* Good, because 設定の場所がワークスペースの外に限られ、モデルが自分の制限を書き換えられない。
* Bad, because 設定を誤れば `~/.aws` のような認証情報のディレクトリを見せられる。ホームそのものは拒否するが、その下の個別のディレクトリまでは判断しない。
* Bad, because ネットワークが要る作業 (依存の取得、push) は相変わらず外でやる。

### Confirmation

`settings.rs` のテストで、危険なマウントの拒否、存在しないディレクトリの警告、PATH の制限、予約された変数の拒否、時間の範囲、`config.toml.example` が誤りなく読めることを確かめる。`execution/tests.rs` の `user_mounts_path_and_env_reach_commands_read_only` で、設定したディレクトリの実行ファイルが PATH から動き、変数が届き、書き込みは拒否され、設定が無ければ見えないことを確かめる。ワークスペースが設定ディレクトリを含むと起動しないことも確かめる。手元では、例の設定で crates.io 依存のプロジェクトの `cargo run --offline` がサンドボックス内で成功した。

## Pros and Cons of the Options

### 固定のまま

* Good, because 保証が最も単純。
* Bad, because Nix で道具を入れ、依存をプロジェクト内に置ける利用者しか検証まで回せない。

### 設定ファイルで宣言する

* Good, because モデルの出力が権限を決めない。
* Good, because 既定は空で、足した分が起動時に見える。
* Bad, because 利用者が自分の環境の道具の置き場所を知る必要がある。

### 承認ダイアログでその場の権限拡大を許す

* Good, because 柔軟。
* Bad, because モデルの出した要求を人が評価する形に戻り、要求を通すために繰り返し尋ねる誘因ができる。

### ホスト全体を読み取り可にする

* Good, because 設定が要らない。
* Bad, because `~/.ssh` などが読め、読んだ内容はモデルに送られうる。socium の隔離の強みを捨てる。
