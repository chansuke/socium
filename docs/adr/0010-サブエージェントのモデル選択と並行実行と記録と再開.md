# サブエージェントのモデル選択と並行実行と記録と再開

## Context and Problem Statement

ADR 8 と ADR 9 で、`agent` tool による同期のサブエージェントと、利用者が定義する種類を入れた。Claude Code と Codex CLI と比べて、次の三点が足りない。

* 呼び出しごとにモデルを選べない。種類にモデルを書かない限り、簡単な検索にも親と同じ高価なモデルを使う。Claude Code の `Agent` tool は呼び出しごとに `model` を受け付ける。
* 一つの応答にある複数の委任が一件ずつ動き、その間は親が止まる。Claude Code は同じ応答の複数の `Agent` 呼び出しを同時に動かす。
* 子の message を保存しないので、後から見返せず、続きを頼めない。Codex CLI は `send_input` で動いている子に追加の指示を送り、Claude Code は終わった子を ID で再開できる。

## Decision Drivers

* ADR 8 の安全の性質（渡した tool の強制、入れ子の禁止、一度に一件の承認、取り消し）を保つ。
* 費用と送り先を利用者が把握できる。キーの無いモデルに黙って切り替えない。
* 再起動をまたいで、子が何をしたかを確かめられる。

## Considered Options

* 同期のまま、条件を満たす呼び出しだけを同時に動かし、終わった子を ID で再開する
* Codex CLI のように子を非同期に起こし、`wait` と `send_input` で管理する

## Decision Outcome

Chosen option: 「同期のまま、条件を満たす呼び出しだけを同時に動かし、終わった子を ID で再開する」。ADR 8 の一度に一件の承認と、順に実行する tool loop を崩さずに、待ち時間と見返し・続きの不足を埋められる。

### モデルの選択

* 起動時に、registry のモデルのうち provider を組み立てられる（API キーがある）ものを、サブエージェント用に用意する。
* `agent` tool に任意の入力 `model` を足す。値は用意したモデルの alias に限り、tool の説明にそれぞれの説明を載せる。用意したモデルが無ければ、この入力は出さない。
* 子のモデルは、呼び出しの `model`、種類の `model`、親の現在のモデルの順に決める。種類の `model` も同じ一覧から引くので、起動時にキーの無いモデルを名指しする種類は ADR 9 のとおり読み込まない。
* 一覧に無い alias は、子を動かす前に、選べる alias を示す誤りとして返す。

### 並行実行

* 一つの応答で続けて並ぶ `agent` 呼び出しのうち、新しく起こす子で、種類が workspace を変えられない（tool がすべて読み取り専用の）ものを、まとめて同時に動かす。`worker` や書き込む tool を持つ種類、`resume`、ほかの tool の呼び出しが間に入ると、そこで区切り、従来どおり一件ずつ動かす。
* 同時に動かすのは、承認を求めず、同じファイルを変えない子に限る。今の `TaskControl` は一度に一件の承認しか待てず、複数の子の編集の順序と取り消し履歴の整合を保証する仕組みが無いため。モデルの書いた順序を変えないよう、続けて並ぶ呼び出しだけをまとめる。
* まとめた呼び出しの意図（`tool_started`）をすべて保存してから動かし始める。結果は、子が終わるたびに会話の呼び出しの順の位置に入れて保存する。途中で止まっても、終わった子の報告は残る。まだ動いていた子は、再起動のときに結果不明として呼び出しの順の位置に補う。会話欄の項目は、全員が終わった後に呼び出しの順で出す。再起動後に会話から組み立てる並びと同じにするため。Activity の `ToolFinished` は、それぞれの子が終わった時点で出す。
* 子は同じ thread の上で交互に進む。provider の応答を待つ間に他の子が進むので、時間の大半を占めるモデルの待ち時間が重なる。tool の実行（ファイルの読み込みや検索）は同期なので、その間は他の子が止まる。
* Activity の記録は、子の round が終わるとき、同時に動く他の子の書きかけの stream を捨てない。

### 記録と再開

* 子の会話を、`.socium/agents/<id>.json` に一つずつ保存する。ID は子を起動した `agent` 呼び出しの call ID から、英数字、`-`、`_` 以外を `_` に置き換えて作り、既にあれば `-2` などを付ける。
* 記録には種類、`description`、最後に動いたモデルの ID、状態（`running`、`finished`、`failed`、`cancelled`）、指示を受けた回数、更新時刻、message を持つ。
* 子の最初の request の前と、親の会話と同じ checkpoint（tool の意図の前、各結果の後）で保存する。子が起こす副作用は、その意図が保存されてから始まる。最初の保存に失敗したら子を動かさない。
* 報告の末尾の一行に ID を入れる。`agent` tool の任意の入力 `resume` に ID を渡すと、保存した message の後に新しい `prompt` を足して、同じ子を続ける。`agent_type` は記録と同じでなければならない。
* 再開するときは、crash で結果の無い tool 呼び出しを結果不明として補う。保存したモデルと違うモデルで続ける場合は、thinking を取り除く。
* `resume` の値はモデルが書くので、英数字、`-`、`_` 以外を含む値を拒否し、`.socium/agents` の外を読ませない。
* 新しい子を起こすとき、更新の古い記録から消し、100 件を残す。
* TUI の `/agents` で保存した子の一覧を、`/agents <id>` でその会話を出す。

Codex CLI の `send_input` のように動いている子へ指示を送る形にはしない。子は同期に動くので、親が次の指示を出せるのは子が終わってからになる。終わった子を ID で続ける形で足りる。

### Consequences

* Good, because 複数の調査を同時に進め、待ち時間を短くできる。
* Bad, because 同時に動くのは読み取りだけの子に限る。編集を伴う委任は一件ずつのまま。
* Good, because 再起動の後でも、子が何を読み何をしたかを確かめられる。
* Good, because 調査の続きを、同じ文脈を読み直させずに頼める。
* Bad, because 記録が `.socium/` に溜まる。100 件で古いものから消す。
* Good, because 簡単な検索を小さいモデルに任せ、費用と待ち時間を減らせる。
* Good, because 選べるモデルが起動時に決まり、キーの無いモデルへの request が起きない。
* Bad, because tool の説明が、登録したモデルの数だけ長くなる。

### Confirmation

core のテストで、二つの `explorer` の子が互いを待たないと応答できない provider で、同時に動いて結果が呼び出しの順に返ること（まとめ実行を外すとこのテストが時間切れで失敗することも確かめた）、まとめる範囲（読み取りだけの新しい子が続く間だけで、`worker`、`resume`、ほかの tool、知らない種類で区切る）、同時に動く子の書きかけの stream が Activity の記録に残ることを確かめる。

まとめた三つの子のうち両端の二つが終わり、真ん中が動いている間に止まった会話を再起動すると、終わった二つの報告が残り、真ん中だけが結果不明になり、結果が呼び出しの順に並ぶことを確かめる。

子の会話が保存され、`resume` で保存した message の後に新しい指示を足して続くこと、知らない ID、パスのような ID、違う種類の再開を拒否すること、失敗した実行も tool の結果ごと保存されること、crash で途切れた tool 呼び出しを再開時に結果不明として補うこと、ID の作り方と重複の回避、100 件を超えた古い記録を消すことを確かめる。TUI のテストで `/agents` の一覧と会話の表示を確かめる。

呼び出しの `model` が子の request のモデル ID になること、一覧に無い alias が誤りになること、種類の `model` が使われること、キーのあるモデルだけが `model` の列挙に載ることを確かめる。

## Pros and Cons of the Options

### 同期のまま、条件を満たす呼び出しを同時に動かす

* Good, because 承認、取り消し、保存の仕組みを変えずに済む。
* Good, because 親のモデルから見て、tool の結果が同じ round で返る形のまま。
* Bad, because 編集を伴う子は同時に動かせず、子の実行中は親が止まる。

### 非同期の子と管理用の tool 群

* Good, because 親が子の実行中も作業でき、動いている子に指示を足せる。
* Bad, because 承認の要求が複数の子から同時に来うる。今の `TaskControl` は一件しか持てない。
* Bad, because 子の状態を turn をまたいで持ち、再起動で復元し、同じファイルの同時の編集を防ぐ仕組みが要る。

## More Information

Claude Code の `Agent` tool の `model` と再開、同時実行は公開文書（https://docs.anthropic.com/en/docs/claude-code/sub-agents ）、Codex CLI の `spawn_agent`、`send_input`、`wait` は openai/codex の multi-agent の handler を、2026-11-14 に確認した。関連: ADR 8、ADR 9。
