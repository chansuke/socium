# サブエージェントのモデル選択と並行実行と記録と再開

## Context and Problem Statement

ADR 8 と ADR 9 で、`agent` tool による同期のサブエージェントと、利用者が定義する種類を入れた。Claude Code と Codex CLI と比べて、次の三点が足りない。

* 呼び出しごとにモデルを選べない。種類にモデルを書かない限り、簡単な検索にも親と同じ高価なモデルを使う。Claude Code の `Agent` tool は呼び出しごとに `model` を受け付ける。
* 一つの応答にある複数の委任が一件ずつ動き、その間は親が止まる。Claude Code は同じ応答の複数の `Agent` 呼び出しを同時に動かす。
* 子の message を保存しないので、後から見返せず、続きを頼めない。Codex CLI は `send_input` で動いている子に追加の指示を送り、Claude Code は終わった子を ID で再開できる。

## Decision Drivers

* ADR 8 の安全の性質（渡した tool の強制、入れ子の禁止、一度に一件の承認、取り消し）を保つ。
* 費用と送り先を利用者が把握できる。キーの無いモデルに黙って切り替えない。
* 再起動をまたいで、子が何をしたかを確かめられる。

## Considered Options

* 同期のまま、条件を満たす呼び出しだけを同時に動かし、終わった子を ID で再開する
* Codex CLI のように子を非同期に起こし、`wait` と `send_input` で管理する

## Decision Outcome

Chosen option: 「同期のまま、条件を満たす呼び出しだけを同時に動かし、終わった子を ID で再開する」。ADR 8 の一度に一件の承認と、順に実行する tool loop を崩さずに、待ち時間と見返し・続きの不足を埋められる。

### モデルの選択

* 起動時に、registry のモデルのうち provider を組み立てられる（API キーがある）ものを、サブエージェント用に用意する。
* `agent` tool に任意の入力 `model` を足す。値は用意したモデルの alias に限り、tool の説明にそれぞれの説明を載せる。用意したモデルが無ければ、この入力は出さない。
* 子のモデルは、呼び出しの `model`、種類の `model`、親の現在のモデルの順に決める。種類の `model` も同じ一覧から引くので、起動時にキーの無いモデルを名指しする種類は ADR 9 のとおり読み込まない。
* 一覧に無い alias は、子を動かす前に、選べる alias を示す誤りとして返す。選べるモデルが一つも無ければ、`model` を省いて現在のモデルで動かすよう示す。
* 起動時に、用意したモデルが無視する設定（`EFFORT` など）を、その alias を名指しする警告として一度ずつ出す。現在のモデルの警告と同じものは重ねない。

### 並行実行

* 一つの応答で続けて並ぶ `agent` 呼び出しのうち、新しく起こす子で、種類が workspace を変えられない（tool がすべて読み取り専用の）ものを、まとめて同時に動かす。`worker` や書き込む tool を持つ種類、`resume`、ほかの tool の呼び出しが間に入ると、そこで区切り、従来どおり一件ずつ動かす。
* 同時に動かすのは、承認を求めず、同じファイルを変えない子に限る。今の `TaskControl` は一度に一件の承認しか待てず、複数の子の編集の順序と取り消し履歴の整合を保証する仕組みが無いため。モデルの書いた順序を変えないよう、続けて並ぶ呼び出しだけをまとめる。
* まとめた呼び出しの意図（`tool_started`）をすべて保存してから動かし始める。結果は、子が終わるたびに会話の呼び出しの順の位置に入れて保存する。途中で止まっても、終わった子の報告は残る。まだ動いていた子は、再起動のときに結果不明として呼び出しの順の位置に補う。会話欄の項目は、全員が終わった後に呼び出しの順で出す。再起動後に会話から組み立てる並びと同じにするため。Activity の `ToolFinished` は、それぞれの子が終わった時点で出す。
* 子は同じ thread の上で交互に進む。provider の応答を待つ間に他の子が進むので、時間の大半を占めるモデルの待ち時間が重なる。tool の実行（ファイルの読み込みや検索）は同期なので、どの tool 呼び出しも別の thread で動かし、その間も他の子の stream と tool が進む。進み具合の通知と実行前の保存は、呼び出した子の側で順に行う。
* Activity の記録は、子の round が終わるとき、同時に動く他の子の書きかけの stream を捨てない。
* TUI の Activity 欄は、子の item をそれを起動した `agent` 呼び出しの item の下に、子ごとにまとめて並べる。届いた順に並べると、交互に届く子の item が最後の `agent` 行の下に混ざり、どの子の手順か読めないため。tool item は `agent` と call ID の組で照合する。子どうしが同じ call ID を使っても、別の item になる。

### 記録と再開

* 子の会話を、`.socium/agents/<id>.json` に一つずつ保存する。ID は子を起動した `agent` 呼び出しの call ID から、英数字、`-`、`_` 以外を `_` に置き換えて作り、既にあれば `-2` などを付ける。
* 記録には種類、`description`、最後に動いたモデルの ID、状態（`running`、`finished`、`failed`、`cancelled`）、指示を受けた回数、更新時刻、message、実行した tool 呼び出しごとの `tool_started`（どう許可されたか）を持つ。`tool_started` の無い古い記録はそのまま読める。
* 子の最初の request の前と、親の会話と同じ checkpoint（tool の意図の前、各結果の後）で保存する。子が起こす副作用は、その意図が保存されてから始まる。最初の保存に失敗したら子を動かさない。
* 報告の末尾の一行に ID を入れる。`agent` tool の任意の入力 `resume` に ID を渡すと、保存した message の後に新しい `prompt` を足して、同じ子を続ける。`agent_type` は記録と同じでなければならない。
* 再開するときは、crash で結果の無い tool 呼び出しを結果不明として補う。保存したモデルと違うモデルで続ける場合は、thinking を取り除く。
* `resume` の値はモデルが書くので、英数字、`-`、`_` 以外を含む値を拒否し、`.socium/agents` の外を読ませない。
* 新しい子を起こすとき、更新の古い記録から消し、100 件を残す。起こしたばかりの子の記録は、時計が戻って他より古く見えても消さない。
* TUI の `/agents` で保存した子の一覧を、`/agents <id>` でその会話を出す。利用者が承認して実行した呼び出しには、親の会話と同じく `(approved)` を付ける。

Codex CLI の `send_input` のように動いている子へ指示を送る形にはしない。子は同期に動くので、親が次の指示を出せるのは子が終わってからになる。終わった子を ID で続ける形で足りる。

### Consequences

* Good, because 複数の調査を同時に進め、待ち時間を短くできる。
* Bad, because 同時に動くのは読み取りだけの子に限る。編集を伴う委任は一件ずつのまま。
* Good, because 再起動の後でも、子が何を読み何をしたかを確かめられる。
* Good, because 調査の続きを、同じ文脈を読み直させずに頼める。
* Bad, because 記録が `.socium/` に溜まる。100 件で古いものから消す。
* Good, because 簡単な検索を小さいモデルに任せ、費用と待ち時間を減らせる。
* Good, because 選べるモデルが起動時に決まり、キーの無いモデルへの request が起きない。
* Bad, because tool の説明が、登録したモデルの数だけ長くなる。

### Confirmation

core のテストで、二つの `explorer` の子が互いを待たないと応答できない provider で、同時に動いて結果が呼び出しの順に返ること（まとめ実行を外すとこのテストが時間切れで失敗することも確かめた）、まとめる範囲（読み取りだけの新しい子が続く間だけで、`worker`、`resume`、ほかの tool、知らない種類で区切る）、同時に動く子の書きかけの stream が Activity の記録に残ること、同時に動く子がそれぞれ一度ずつ同じファイルを読んでも堂々巡りのシグナルが出ず、一つの子が繰り返せば出ることを確かめる。TUI のテストで、交互に届く二つの子の item がそれぞれの `agent` 行の下にまとまり、再生でも同じ並びになること、同じ call ID を使う二つの子の tool が別の item になることを確かめる。

二つの `explorer` の子がそれぞれ名前付き pipe を検索し、pipe の書き手が両方の検索が pipe を開くまで書かないとき、どちらの検索も一致を返し、二つの検索の期間が重なることを確かめる。一件ずつ動くと、先の検索が 5 秒の期限で失敗する。

まとめた三つの子のうち両端の二つが終わり、真ん中が動いている間に止まった会話を再起動すると、終わった二つの報告が残り、真ん中だけが結果不明になり、結果が呼び出しの順に並ぶことを確かめる。

子の会話が保存され、`resume` で保存した message の後に新しい指示を足して続くこと、知らない ID、パスのような ID、違う種類の再開を拒否すること、失敗した実行も tool の結果ごと保存されること、crash で途切れた tool 呼び出しを再開時に結果不明として補うこと、ID の作り方と重複の回避、100 件を超えた古い記録を消すことを確かめる。TUI のテストで `/agents` の一覧と会話の表示を確かめる。

呼び出しの `model` が子の request のモデル ID になること、一覧に無い alias が誤りになること、種類の `model` が使われること、キーのあるモデルだけが `model` の列挙に載ることを確かめる。

## Pros and Cons of the Options

### 同期のまま、条件を満たす呼び出しを同時に動かす

* Good, because 承認、取り消し、保存の仕組みを変えずに済む。
* Good, because 親のモデルから見て、tool の結果が同じ round で返る形のまま。
* Bad, because 編集を伴う子は同時に動かせず、子の実行中は親が止まる。

### 非同期の子と管理用の tool 群

* Good, because 親が子の実行中も作業でき、動いている子に指示を足せる。
* Bad, because 承認の要求が複数の子から同時に来うる。今の `TaskControl` は一件しか持てない。
* Bad, because 子の状態を turn をまたいで持ち、再起動で復元し、同じファイルの同時の編集を防ぐ仕組みが要る。

## More Information

Claude Code の `Agent` tool の `model` と再開、同時実行は公開文書（https://docs.anthropic.com/en/docs/claude-code/sub-agents ）、Codex CLI の `spawn_agent`、`send_input`、`wait` は openai/codex の multi-agent の handler を、2026-11-14 に確認した。関連: ADR 8、ADR 9。

### 後の変更

違うモデルで再開するときに thinking を取り除くのはやめた。記録には残し、送るときに送り先が読めるものだけを送る ([ADR 14](0014-応答ごとに出所を記録しthinkingは読める送り先にだけ送る.md))。

子は自分の履歴を圧縮しなかった。tool loop の途中で窓が埋まると失敗し、その記録を再開しても model を呼ぶ前に同じ失敗を繰り返した。失敗した再開も指示を記録に足すので、記録は伸びるだけだった (2026-11-16 の再現)。親の会話の圧縮 ([ADR 15](0015-組み込みモデルの窓を実値にしtool結果に上限を設けて窓が埋まったら縮めて圧縮する.md)) を、同じ処理のまま子にも使う。

* 記録に、親の会話と同じ要約の状態 (要約が覆う message の数、要約、thinking を送ってよい位置、最初の依頼) を持たせる。message はすべて残し、送るときの写しだけを要約で置き換える。`/agents <id>` は全体を出す。
* 子の tool loop を始める前に、履歴の推定が子のモデルの入力予算を超えていれば圧縮する。再開の前も、窓が埋まって tool loop が止まった後も同じにする。圧縮の後は親と同じ組み立てで写しを作り、まだ超えれば古い message を決定的な要約に回し、残す message の中の古い tool 結果から縮める。
* 窓が埋まって止まった tool loop は、要約から続ける。親では利用者が続きを頼むが、子には頼む人がいないため。round の番号は 1 に戻さず止まった round の番号から続け、`MAX_TOOL_ROUNDS` は一回の実行の合計に掛かる。続けた tool loop が一度も応答を得ずにまた止まったら、続けずに失敗を返す。
* 要約するモデルは、親のモデルで動く子なら親と同じ (`compact_model`、無ければ親のモデル)、別のモデルで動く子ならそのモデルの `compact_model` にする。その alias がサブエージェント用に用意したモデルに無ければ、子のモデル自身で要約する。要約モデルが失敗したら、親と同じく一行ずつの要約を残し、理由を警告に出す。
* 圧縮は子の Activity として `agent` 呼び出しの下に出し、親の会話の欄には出さない。報告は普段どおり親に返る。
* 再開で足した指示に子のモデルが一度も応答しないまま失敗したら、その指示を記録から外し、指示を受けた回数も戻す。状態は `failed` (取り消しなら `cancelled`) にする。同じ指示で再開し直しても、応答の無い指示が重ならない。最初の指示は子の課題そのものなので、失敗しても残す。

* Good, because 長い調査で窓を埋めた子も報告を返し、その後も再開できる。
* Good, because 要約の選び方、残す範囲、thinking の扱い、失敗時の代わりの要約が親と一つの実装になる。
* Bad, because 子は入力予算を超えるまで圧縮しない。tool loop の途中では親の閾値 (既定 20 万トークン) を確かめないので、再開の前もそれに揃えた。窓の大きいモデルでは、圧縮の前の round が高くつく。
* Bad, because 要約した後の子は、要約の前に読んだ内容の細部を失う。

core のテストで、窓の小さいモデルの子が tool loop の途中で窓を埋めても、そのモデルの `compact_model` で要約し、要約から続けて報告を返すこと、すべての request が窓に収まること、Activity に子の圧縮が出ること、入力予算を超えた記録の再開で、先に親の要約モデルで要約してから子のモデルを呼ぶこと、応答の無いまま失敗した再開が記録を変えないことを確かめる。

* 2026-11-16: 記録を、子を起動したセッションの `.socium/sessions/<session>/agents/<id>.json` に置くようにした。workspace 全体の `.socium/agents/` では、セッションを一覧から消しても子の記録（与えた指示と読んだファイルの中身）が残り、`/agents` が他のセッションの子まで出していた。セッションの directory の下に置けば、消すと記録も消え、一覧と `resume` は開いているセッションの子だけを見る。記録に `session_id` の項目を足す形は、消すときと一覧のときに全件を読んで絞る必要があり、消し漏れが起きうるので採らなかった。
  * `resume` は開いているセッションの記録だけを探す。他のセッションの ID は、このセッションで起動した子しか再開できないという誤りになる。
  * 100 件の上限はセッションごとに数える。
  * `.socium/agents/` にある前の記録は、次の起動（または `-r` の一覧）で、メッセージのある最も新しく保存したセッション（`-c` で続くもの）へ移す。どのセッションで起動したかは記録に無いため。同じ ID の記録がそのセッションにあれば上書きせずに残す。メッセージのあるセッションが無い間は移さない。
