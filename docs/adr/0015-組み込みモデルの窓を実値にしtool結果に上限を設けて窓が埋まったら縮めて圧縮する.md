# 組み込みモデルの窓を実値にしtool結果に上限を設けて窓が埋まったら縮めて圧縮する

## Context and Problem Statement

組み込みの `opus`・`sonnet`・`haiku` は窓を持たず、既定の 20 万トークンから出力枠 6.4 万を引いた 13.6 万が入力予算だった。Anthropic のモデル表では 3 つとも 100 万トークンである。1 ターンの tool 結果がこの予算を超えると、次のラウンドの前に失敗し、読んだ内容はモデルに一度も渡らなかった。`/compact` は直近 16 メッセージを残すので何もせず、次の送信は末尾 8 メッセージを必ず残すために 7 回続けて失敗した (2026-11-14 のレビュー N3、再現 R3)。要約は 1 メッセージ 600 文字で入力を切り、長い依頼の後半を落とした (N7、再現 R5)。上限の多くは、理由が記録されていない定数から来ていた。

## Decision Drivers

* 長いターンが失敗せず、失敗しても次の送信で回復する。
* 読んだ内容と依頼の要件を、要約で失わない。
* 生の履歴は書き換えず、送るときの写しだけを変える。ただし、モデルに見せたものは、そのまま記録に残す。
* 3 つの接続形式で同じ挙動にする。

## Considered Options

* 窓を実値にし、1 つの tool 結果に上限を設け、窓が埋まったら縮めて、それでも足りなければターンを止めてすぐ圧縮する
* ターンの途中で同期に要約して続ける
* Anthropic のサーバー側の compaction と context editing を使う

## Decision Outcome

Chosen option: 「窓を実値にし、結果に上限を設け、埋まったら縮めて圧縮する」。窓を実値にするだけで頻度は大きく下がり、残る形 (巨大な結果、長い会話) にはそれぞれの段で答えられる。

* 組み込みの 3 モデルの窓を 100 万トークンにする。`CONTEXT_WINDOW_TOKENS` はすべてのモデルの窓を置き換え、注入された lookup から読む。
* 圧縮を始める点を窓と別に持つ。既定は 20 万トークンと入力予算の 80% の小さいほう。`models.toml` の `compact_at_tokens` か `COMPACTION_TOKEN_THRESHOLD` で変える。長いプロンプトはラウンドごとの費用が上がり、モデルの注意も散るので、100 万を埋めてから圧縮はしない。
* 1 つの tool 結果は 10 万文字を超えたら先頭と末尾を残す。`read_file` は既定で 2,000 行ずつ返し、続きの位置を示す (N12)。
* ラウンドの前に推定が予算を超えたら、最新のラウンドの結果を大きい順に、先頭と末尾を残して縮める (1 件 2,000 文字まで)。最新の結果より後に作られた thinking は無いので、thinking は有効なまま。縮めた結果をモデルに見せ、そのまま記録に残す。それでも超えたら、ターンを止め、その場で圧縮し、続けるよう案内する。
* ターンの前の組み立てで予算を超えたら、残すメッセージを最新の 1 件まで減らし、それでも超えれば残すメッセージの中の古い tool 結果から縮める。縮めた結果より後の thinking は送らない。
* 圧縮で残すのは、直近 16 メッセージのうち約 2 万トークンに収まる分にする。巨大な結果が直近にあっても `/compact` が何もしない状態にならない。
* 推定は各ラウンドの実測と比べて補正する (0.5〜3 倍)。日本語のように文字数÷3.5 が少なく見積もるテキストでも予算を超えない。
* 要約: ユーザーの発言は 8,000 文字まで要約モデルに渡し、最初の依頼は要約とは別に原文で保持して、要約の message に入れる。要約モデルの出力上限は 8,000 トークン (thinking を含む)。要約モデルが失敗した理由は Activity の警告と `/compact` の結果に出す。
* 状態行の残量は入力予算に対する割合にする。空の会話は 100% 近くから始まる。

### Consequences

* Good, because 再現 R3 の 3 つの 199 KB の読み込みがモデルに届き、ターンが成功する。
* Good, because 窓が埋まっても、次の送信で回復する。
* Good, because 長い依頼の後半の要件が要約を越えて残る。
* Bad, because 縮めた結果は記録にも縮めたまま残る。全文は tool を呼び直さないと見られない。コマンドの出力は `.socium/outputs/` に残る。
* Bad, because ターンの途中では要約しない。窓が埋まったターンは止まり、利用者が続きを頼む。

### Confirmation

信頼性テストで、R3 と同じ 3 つの大きい読み込みが 20 万の窓でもモデルに届くこと、最新のラウンドの結果が縮められ、送ったものと記録が同じであること、縮めきれない場合にターンが止まり、その場で圧縮され、次の送信が通ることを確かめる。`context.rs` と `compaction.rs` のテストで、縮める処理が必ず止まること、残す範囲がトークンでも絞られること、閾値の決め方、残量の割合を確かめる。要約のテストで、ユーザーの発言の末尾の要件と最初の依頼が残り、要約モデルの失敗の理由が報告されることを確かめる。

## Pros and Cons of the Options

### 窓を実値にし、上限と縮小と即時圧縮を組み合わせる

* Good, because どの接続形式でも同じに動く。
* Good, because 送る写しは決定的で、キャッシュの接頭辞を壊しにくい。
* Bad, because 段が多く、どの段が効いたかを Activity の警告で示す必要がある。

### ターンの途中で同期に要約する

* Good, because ターンを止めずに続けられる。
* Bad, because 実行中の tool ループの意図と結果の保存 (逐次の checkpoint) と、生の履歴と写しの対応が複雑になる。要約の失敗がターンの失敗になる。

### サーバー側の compaction と context editing

* Good, because Anthropic では最も効率がよい。
* Bad, because 他の接続形式で同じ挙動にできない。
