# 承認を取り消しにくい操作に絞りセッション単位の許可を持つ

## Context and Problem Statement

コマンドとコミットは毎回 1 回限りの承認が要り、120 秒答えなければ拒否された。拒否は「承認が要る」とだけ伝わり、モデルは同じ要求を繰り返した。一方で、ホストが自分で実行するファイル (`build.rs`、`.envrc`、CI の定義) の編集と、認証情報を含みうるファイルの読み取りは、承認なしに通った (2026-11-14 のレビュー N8、N9、再現 R16)。承認が何を守るためのものかを決める。所有者は「Claude Code や Codex のやり方に倣う」と決めた。

## Decision Drivers

* 承認は、サンドボックスの外へ効果が及ぶ操作と、取り消しにくい操作に向ける。サンドボックスの代わりにはしない。
* 同じ種類の要求を何度も尋ねない。離席しても拒否扱いにしない。
* 承認を答えられる人がいない実行 (headless) で、黙って許可しない。
* 拒否されたら、モデルが別の手を考えるように伝える。

## Considered Options

* 毎回承認のまま (現状)
* サンドボックス内のコマンドは自動、`git_commit` だけ承認
* 既定は尋ね、その場で「このセッション中は許可」を選べ、設定で規則と自動実行を宣言できる

## Decision Outcome

Chosen option: 「既定は尋ね、セッション中の許可と設定の規則を持つ」。Claude Code は Bash を既定で尋ね、「以後このコマンドは尋ねない」を選べ、設定の `permissions.allow`・`deny` で前置きの規則を持つ。Codex CLI はサンドボックスの中では尋ねずに実行する方式を選べる。この二つを、socium のサンドボックスの強さに合わせて組み合わせた。

* `run_command`:
  * 設定の `approval.deny` に argv の前置きが一致すれば、尋ねずに拒否する。
  * `approval.allow` に一致するか、このセッションで許可した前置きに一致するか、`approval.commands = "auto"` なら、尋ねずに実行する。ただし誰も見ていないコマンドは狭いサンドボックスで動かす: 認証情報を含みうるファイル (`approval.sensitive`) は空のファイルに置き換え、ホストが実行するファイル (`approval.protected`) は読み取り専用にする。これらを時間内に列挙できなければ尋ねる。
  * それ以外は尋ねる。選択肢は「1 回だけ許可」「このセッション中はこの前置きを許可」「拒否」。前置きはプログラムと、続く単語の引数を最大 2 つ (オプションや記号を含む引数の手前まで) で、`cargo test` や `git status` になる。`sh`・`bash`・`env`・`xargs`・`sudo`・`find` のような何でも実行できる道具と、`python -m` のないインタープリタには出さない。
* `git_commit` は常に尋ね、差分、新しいファイルの全文、author を見せる。承認の間に変わったら拒否する。
* `approval.protected` に当たる編集は、モードを問わず尋ね、編集の差分を見せる。承認の間にファイルが変わったら拒否する。既定の一覧は direnv・mise・Nix・rust-analyzer (build script、Cargo の設定、toolchain)・エディタ・CI・hook 管理の設定。
* `approval.sensitive` に当たる読み取りは、モードを問わず尋ねる。読んだ内容はモデルの送り先に渡るため。既定の一覧は `.env` (例のファイルは除く)、`.envrc`、`.netrc`、各種の認証ファイル、鍵。
* 承認に期限は無い。待っている間に取り消せる。
* 答える人がいない実行 (headless の `-p`、子プロセスからの利用) では、承認が要る呼び出しを拒否し、`config.toml` で許可する方法をモデルに伝える。
* 拒否は「繰り返さず、必要なら利用者に尋ねる」とモデルに伝える。

### Consequences

* Good, because 同じコマンドを何度も尋ねない。離席しても拒否扱いにならない。
* Good, because ホストが後で実行するファイルの編集と、秘密の読み取りが、必ず人の目を通る。
* Good, because 自動実行を選んでも、誰も見ていないコマンドは秘密を読めず、ホストが実行するファイルを変えられない。
* Bad, because セッション中の許可は前置きの一致なので、許可した `cargo test` の後ろに何を付けても通る。サンドボックスの外には出ない。
* Bad, because 保護と秘密の一覧は名前の規則で、プロジェクト固有の実行ファイルまでは知らない。設定で足す。

### Confirmation

`approval.rs` のテストで、拒否規則が許可より強いこと、自動と許可の規則が制限付きで動くこと、シェルや wrapper に前置きを出さないこと、保護と秘密がモードを問わず尋ねること、保護の編集の承認に差分が付くことを確かめる。`control.rs` のテストで、セッション中の許可が提示した前置きだけを覆い、期限なく答えを待つことを確かめる。信頼性テストで、自動実行のコマンドが秘密を読めずホストのファイルを変えられないこと、セッション中の許可で 2 回目を尋ねないこと、答える人がいない実行が `config.toml` を案内すること、承認の間に変わった保護ファイルを編集しないことを確かめる。TUI のテストで、選択肢と番号キー、`a` での許可を確かめる。

## Pros and Cons of the Options

### 毎回承認のまま

* Good, because 取り消せない変更を必ず人が見る。
* Bad, because 長いタスクを任せられず、承認疲れで中身を読まずに許可する誘因になる。
* Bad, because ホストが実行するファイルの編集と秘密の読み取りは守っていなかった。

### サンドボックス内のコマンドは自動、コミットだけ承認

* Good, because 離席して任せられる。
* Bad, because コマンドによる変更は編集の履歴に入らず、元に戻せない。秘密の読み取りも通る。

### 既定は尋ね、セッション中の許可と設定の規則を持つ

* Good, because 利用者が自分の信頼の度合いに合わせて選べる。
* Neutral, because 規則の書き方 (前置きの一致) を利用者が知る必要がある。
