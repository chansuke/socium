# デスクトップ操作をホスト上の有効化とアプリ単位の許可に限って認める

## Context and Problem Statement

Socium のモデルはホストの GUI のアプリを操作できない。作った GUI の確認や、コマンドのないアプリの操作は、利用者が代わりに行っている。

デスクトップの操作では、Socium が画面を撮ってモデルへ送り、モデルが返したクリックやキー入力をホストで実行する。Anthropic と OpenAI は、そのための組み込みの tool を持つ。両者の文書は専用の VM かコンテナで動かすことを勧めている。

利用者の実際のデスクトップで動かすと、次の 3 つが起きうる。

* モデルは端末のウィンドウに文字を打つだけで、サンドボックスの外でコマンドを実行できる。
* モデルは Socium 自身の承認の画面を操作できる。web のクライアントでは、承認のボタンはホストのブラウザに表示される ([docs/clients.md](../clients.md))。
* web とモバイルのクライアントはホストから離れた場所で同じ会話に加わる。端末の認証情報が漏れると、漏れた先からホストのデスクトップを操作できる。

デスクトップの操作を認める条件と範囲を決める。

## Decision Drivers

* モデルが自分の要求を自分で承認できない。
* ホストの前にいない人が操作を始められない。
* 画面のうち、許可したアプリ以外をプロバイダへ送らない。
* 接続形式ごとの組み込みの tool の違いを、core に持ち込まない。
* 操作の対象を後から足せる。

## Considered Options

* 実際のデスクトップを対象にし、tool の承認だけで守る
* 仮想の画面だけを対象にする
* 実際のデスクトップを対象にし、ホスト上の有効化とアプリ単位の許可で範囲を限る

## Decision Outcome

Chosen option: 「実際のデスクトップを対象にし、ホスト上の有効化とアプリ単位の許可で範囲を限る」。利用者がふだん使うアプリを操作でき、かつ Context に挙げた 3 つのそれぞれに、対応する制御を置けるため。

所有者は 2026-11-20 に、実際のデスクトップを先に作ることと、有効化をホスト上に限ることを承認した。

#### 実装の時期

* 実装は web、デスクトップ、モバイルのクライアントが揃った後に行う。承認の要求に付ける画像、セッション中の許可、有効化を行う場所は、クライアントとのやり取りの形に依存するため。
* デスクトップのクライアントはホストで動く。有効化をそのクライアントから行えるようにするかは、実装の前にこの ADR を見直して決める。
* 「モデルとのやり取り」の節は 2026-11-20 の時点のプロバイダの仕様に基づく。実装の前に、その時点の仕様で確かめ直す。

#### 有効化

* `config.toml` の `[computer]` で有効にする。既定は無効である。
* 設定に加えて、セッションごとの有効化が要る。有効化できるのは、ホストで Socium を起動した人だけである。TUI ではコマンドで、ゲートウェイでは起動の引数で行う。クライアントとのやり取りに、有効化の命令は置かない。
* 承認をすべて省く起動の引数 (`--dangerously-skip-permissions`、[ADR 20](0020-dangerously-skip-permissionsで承認をすべて省く実行を起動の引数に限って許す.md)) は、デスクトップの操作を対象にしない。
* 答える人がいない実行と、サブエージェントには、デスクトップの操作の tool を渡さない。

#### 範囲

* 許可はアプリの単位で持つ。入力を実行する直前に、対象のウィンドウが許可したアプリのものかを確かめる。違えば尋ねる。選択肢に「このセッション中はこのアプリを許可」を置く。
* スクリーンショットには許可したアプリのウィンドウだけを写す。他の部分は塗りつぶす。
* 承認を待っている間は、すべての入力を止める。この判定は core が持つので、承認の画面がどのクライアントにあっても同じに働く。
* Socium を動かしている端末のウィンドウへの入力は断る。
* ブラウザのウィンドウは読むことだけを認める。操作はブラウザの tool ([ADR 27](0027-起動中のchromeにcdpで接続しoriginごとの承認でブラウザを操作する.md)) で行う。
* 承認の要求には操作の対象を示すスクリーンショットを付ける ([ADR 26](0026-tool結果に画像を持たせファイルに保存して参照で渡す.md))。遠隔のクライアントは有効化されたセッションで、表示、停止、操作ごとの承認ができる。
* 利用者がマウスかキーボードを動かしたら、入力を止めて利用者に知らせる。どのウィンドウからでも使える停止のキーを置く。
* モデルが 1 回の応答で複数の操作を返したときは、順に実行し、1 つずつ許可を確かめる。途中で失敗したら、残りは実行しない。

#### モデルとのやり取り

* core は接続形式によらない操作 (スクリーンショット、拡大、クリック、ドラッグ、スクロール、文字入力、キー、待機) を定める。
* プロバイダは要求を組み立てるときに、自分の組み込みの tool に差し替える。組み込みの tool のない接続形式には、通常の tool として出す。
* `models.toml` の `features` に `computer_use` を足す。これと `vision` のあるモデルにだけ出す。
* スクリーンショットはプロバイダの上限に合わせて縮めて送る。モデルが返した座標は、元の大きさに戻して使う。

#### 対象

* 操作の対象は差し替えられる形にする。最初の対象は X11 の実際のデスクトップで、入力と画面の取得は X の拡張で行い、外部のコマンドには頼らない。
* Wayland、仮想の画面、Android のエミュレータは、この ADR では決めない。

### Consequences

* Good, because 利用者がふだん使うアプリを、ログインした状態のまま操作できる。
* Good, because 離れた端末の認証情報が漏れても、有効化されていないセッションでは、デスクトップの操作を始められない。
* Good, because 承認を待つ間は入力が止まるので、モデルは承認の画面を操作できない。
* Bad, because 有効化されたセッションでは、漏れた認証情報で、指示と操作ごとの承認ができる。
* Bad, because 許可したアプリの中では、モデルは利用者として何でもできる。端末のアプリを許可すれば、サンドボックスの外でコマンドを実行できる。
* Bad, because X11 では、アプリは Socium が送った入力と利用者の入力を区別できない。範囲の制御は、Socium が入力の前に行う確認だけに頼る。
* Bad, because 画面がロックされている間は使えない見込みである。離れた場所から始める使い方は、仮想の画面を足すまでできない。
* Bad, because 画面の内容はプロバイダへ送られる。許可したアプリのウィンドウに写るものは、すべて含まれる。

### Confirmation

仮想の X サーバーの上で、テスト用のウィンドウを使って確かめる。許可していないアプリのウィンドウへの入力が尋ねること、スクリーンショットで他のウィンドウが塗りつぶされること、承認を待つ間の入力が実行されないこと、Socium の端末への入力を断ること、縮めた座標が元の位置に戻ることを確かめる。プロバイダごとのテストで、差し替えた要求の形と、複数の操作の途中で失敗したときの結果の形を確かめる。ゲートウェイのテストで、クライアントからの命令では有効化できないことを確かめる。画面がロックされているときの振る舞いは、実機で確かめる。

## Pros and Cons of the Options

### 実際のデスクトップを対象にし、tool の承認だけで守る

* Good, because 実装が小さい。
* Bad, because 承認の画面そのものを操作できる。離れた端末からも始められる。画面の全体がプロバイダへ送られる。

### 仮想の画面だけを対象にする

* Good, because 利用者のデスクトップと認証情報に触れない。画面のロックにも、離れた場所からの利用にも影響されない。プロバイダの勧める形に近い。
* Bad, because 利用者がふだん使うアプリとログインを使えない。仮想の画面で動かすアプリは X のソケットに接続する必要があり、今のサンドボックスはそれを認めていない。

### 実際のデスクトップを対象にし、ホスト上の有効化とアプリ単位の許可で範囲を限る

* Good, because 利用者のアプリを使え、範囲は利用者が選んだアプリに限られる。
* Neutral, because 仮想の画面を後から足せる。そのときは、アプリを動かすサンドボックスを別に決める。
