# 応答全体の期限をやめ接続と無通信の期限と出力前の再試行にする

## Context and Problem Statement

モデルへの HTTP request は、応答全体に 90 秒の期限があった。長い応答は流れ続けていても 90 秒で切れ、同じ依頼を出し直しても同じ所で切れた (2026-11-14 のレビュー N2、再現 R1)。stream は厳格で、知らないイベントの種別が 1 つ来ると応答全体が失敗した。過負荷とレート制限は再試行せず、出力上限で止まった応答は捨てられ、tool の引数の JSON が壊れていればターン全体が失敗した (N11)。Anthropic の stream の資料は「新しいイベントの種別が足されうるので、知らない種別は無視せよ」としている。

## Decision Drivers

* 流れ続ける長い応答を切らない。止まった接続は分かりやすい言葉で切る。
* 一時的な失敗で利用者に作業をやり直させない。ただし表示した出力を巻き戻さない。
* 不正な出力を tool に渡さない。stream の完了と停止理由の検査は緩めない。

## Considered Options

* 接続 30 秒・無通信 180 秒の期限にし、出力が出る前に限って再試行する
* 応答全体の期限を長くする
* 出力の途中でも再試行し、表示をやり直す

## Decision Outcome

Chosen option: 「接続と無通信の期限、出力前の再試行」。

* HTTP client は接続に 30 秒、読み込みの間隔に 180 秒の期限を持つ。応答全体の期限は持たない。SSE の ping も通信に数える。無通信で切れたら「180 秒データが来なかった」と伝える。
* 次の失敗は再試行できる: HTTP 408・409・425・429・500・502・503・504・529、stream の `overloaded_error` と `api_error`、接続の失敗、無通信。`retry-after` があれば従い、無ければ 2・4・8 秒待つ (60 秒まで)。再試行は 3 回まで、出力 (テキスト、thinking、tool の入力) が 1 つも来ていないときだけ。待つ間も取り消せ、Activity に警告を出す。request には副作用が無いので、送り直しても安全。
* 知らないイベント、content block、delta は読み飛ばす。知らない block は履歴に残さない。停止理由と block の完了の検査はそのまま。
* 出力上限 (`max_tokens`) で止まった応答は、tool を呼んでいなければ残し、上限を上げるか続きを頼むよう通知する。tool の呼び出しの途中で止まったものは、引数が切れている可能性があるので誤りにする。`refusal` と `model_context_window_exceeded` は意味の分かる言葉で伝える。
* tool の引数が JSON として読めない呼び出しは実行せず、その呼び出しの誤りとして理由をモデルに返し、ターンは続ける。eager input streaming は API の検証を通らないため。

### Consequences

* Good, because 数分かかる長い応答が最後まで届く。
* Good, because 過負荷やレート制限で利用者が送り直さなくて済む。
* Good, because API が新しいイベントを足しても止まらない。
* Bad, because 出力が始まってから切れた応答は再試行しない。利用者が送り直す。
* Bad, because 知らない block を履歴から外すと、以後の thinking の接頭辞と合わなくなりうる。socium は server tool を使わないので、起きるのは API が通常の応答に新しい種別を足したときに限る。

### Confirmation

ローカルのサーバーで、1 秒の無通信期限のときに 300 ms おきに流れ続ける 1.8 秒の応答が最後まで届き、3 秒止まる応答は 2.5 秒以内に「No data from the provider」で失敗して再試行できる誤りになることを確かめる。信頼性テストで、529 と 429 の後に成功すること、400 は 1 回で失敗し、503 は 4 回で諦めること、壊れた引数の呼び出しが実行されずモデルに理由が返ること、出力上限で止まった応答が通知付きで残ることを確かめる。stream のテストで、知らないイベント・block・delta を読み飛ばし、過負荷を一時的な誤りとして扱うことを確かめる。

## Pros and Cons of the Options

### 接続と無通信の期限、出力前の再試行

* Good, because 期限が「止まった」ことだけを捉える。
* Good, because 表示を巻き戻さない。

### 応答全体の期限を長くする

* Good, because 変更が 1 行。
* Bad, because どの長さでも、それより長い応答は切れる。止まった接続も長く待つ。

### 出力の途中でも再試行する

* Good, because 途中で切れた応答も自動で回復する。
* Bad, because 表示した出力が巻き戻り、tool の意図を保存した後なら二重に実行する危険がある。
