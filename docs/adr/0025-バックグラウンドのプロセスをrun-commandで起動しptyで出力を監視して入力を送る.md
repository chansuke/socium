# バックグラウンドのプロセスをrun_commandで起動しPTYで出力を監視して入力を送る

## Context and Problem Statement

`run_command` はコマンドが終わるまで戻らない。標準入力は閉じてあり、既定では 120 秒で止める。実行中に TUI へ出るのは受け取ったバイト数だけで、出力の本文は終了後にしか見えない。

このため、終わらないコマンド (dev サーバー、ファイル監視、REPL) を扱えない。モデルがそれを起動すると turn は期限まで止まり、期限が来るとプロセスは消える。長いビルドやテストも、終わるまで利用者とモデルのどちらも経過を読めない。

turn をまたいで動き続けるコマンドを、サンドボックスと承認の規則を変えずに扱う方法を決める。

## Decision Drivers

* サンドボックスの方針 (ネットワーク拒否、状態ディレクトリの隠蔽、Socium が終わると子プロセスも終わること) を変えない。
* 利用者とモデルが、終了を待たずに出力を読める。
* 動いているプロセスへの入力で、コマンドの承認規則 ([ADR 13](0013-承認を取り消しにくい操作に絞りセッション単位の許可を持つ.md)) を迂回させない。
* TUI、web、モバイルのどのクライアントからも同じ操作ができる ([docs/clients.md](../clients.md))。

## Considered Options

* 現状のまま、期限だけ延ばす
* すべてのコマンドを対話セッションとして扱う新しいツール一式に置き換える
* `run_command` にバックグラウンドでの実行を足し、出力を読むツールと入力を送るツールを加える

## Decision Outcome

Chosen option: 「`run_command` にバックグラウンドでの実行を足し、出力を読むツールと入力を送るツールを加える」。終わるコマンドの扱いは今のまま残り、既存の承認規則と記録をそのまま使えるため。

以下では、終了を待って結果を返す今の実行を「フォアグラウンド」、待たずに戻る実行を「バックグラウンド」と呼ぶ。

#### 起動と終了

* `run_command` に `background` を足す。真なら、プロセス ID と出力の保存先を返してすぐ戻る。プロセスは turn が終わっても動き続ける。
* バックグラウンドのプロセスは 1 つずつ別のサンドボックスで動く。方針はフォアグラウンドのコマンドと同じで、起動時に決まった「空にするファイル」と「読み取り専用にするパス」は終了まで変えない。
* 利用者は実行中のフォアグラウンドのコマンドをバックグラウンドへ移せる。tool の結果には「利用者がバックグラウンドへ移した」ことと、プロセス ID を書く。
* turn の取り消しはフォアグラウンドのコマンドと turn だけを止める。バックグラウンドのプロセスは一覧から選んで止める。
* Socium が終わると、バックグラウンドのプロセスも終わる。再開したセッションでは「終了済み」として示し、動かし直さない。
* 同時に動かせる数に上限を置く。サブエージェントが起動したバックグラウンドのプロセスは、そのサブエージェントが終わるときに止める。

#### 出力

* 実行中のコマンドの出力の末尾を、進行のイベントに含める。各クライアントは実行中の行にその末尾を表示する。
* `command_output` は、プロセス ID を受けて、前回読んだ位置より後の出力を返す。待つ時間と正規表現を指定でき、一致するか時間が過ぎるまで待つ。
* バックグラウンドのプロセスが終わったときと、指定した正規表現に一致したときは、次のモデル要求の前に通知として履歴へ入れる。利用者の発言とは別の種類として記録する。
* 履歴を圧縮するときは、プロセスの一覧 (ID、コマンド、状態、出力の末尾) を圧縮の入力に含める。
* 保存する出力は先頭と末尾を残して上限で切る。

#### 入力と端末

* バックグラウンドのプロセスの標準入出力は、Socium が作る擬似端末 (PTY) につなぐ。パイプにつなぐと、多くのプログラムは出力を溜めてからまとめて書くので、動いている途中の出力を読めない。
* PTY はそのプロセス専用で、利用者の端末とは別である。`--new-session` と `TERM=dumb` は変えない。残る制御文字はモデルへ渡す前に取り除く。
* `command_input` は、プロセス ID と文字列を受けて、標準入力へ書く。

#### 承認

* バックグラウンドでの起動はフォアグラウンドの `run_command` と同じ判定を通る。
* 人が承認して起動したプロセスへの `command_input` は毎回尋ね、送る文字列を見せる。尋ねなければ、承認済みのシェルへ任意のコマンドを送ることで `approval.allow` と `approval.deny` を迂回できてしまう。選択肢に「このセッション中はこのプロセスへの入力を許可」を加える。
* 尋ねずに起動したプロセス (`approval.commands = "auto"`、`approval.allow`、セッション中の許可) は、起動時から狭いサンドボックスで動いているので、入力も尋ねない。

### Consequences

* Good, because dev サーバーやファイル監視を動かしたまま、次の作業へ進める。
* Good, because 長いビルドの経過を、終了を待たずに利用者とモデルが読める。
* Good, because サンドボックスの方針と、起動時の承認の規則は変わらない。
* Bad, because バックグラウンドのプロセスは Socium の再起動をまたげない。
* Bad, because PTY につないだプログラムは、色や進捗表示の制御文字を出すことがある。取り除いた後の文字列は端末で見た表示と一致しないことがある。
* Bad, because サンドボックスはソケットを作れないので、dev サーバーは起動しても待ち受けができない。この制約はこの ADR では変えない。

### Confirmation

サンドボックスのテストで、バックグラウンドのプロセスがフォアグラウンドと同じ方針で動くこと、Socium の終了と一覧からの停止で子孫まで終わること、上限を超える起動を断ることを確かめる。`process.rs` のテストで、PTY につないだプログラムの出力が行ごとに届くこと、保存した出力が先頭と末尾を残すことを確かめる。承認のテストで、人が承認して起動したプロセスへの入力を毎回尋ねること、セッション中の許可が 1 つのプロセスだけを覆うこと、尋ねずに起動したプロセスへの入力を尋ねないことを確かめる。信頼性テストで、終了の通知が次のモデル要求に入ること、圧縮の後もプロセスの一覧が残ること、再開したセッションがバックグラウンドのプロセスを終了済みとして示すことを確かめる。

## Pros and Cons of the Options

### 現状のまま、期限だけ延ばす

* Good, because 変更が要らない。`sandbox.command_timeout` は既にある。
* Bad, because 終わらないコマンドは扱えない。待っている間、turn は進まない。

### すべてのコマンドを対話セッションとして扱うツール一式に置き換える

* Good, because フォアグラウンドとバックグラウンドの区別がなく、ツールの形が 1 つになる。
* Bad, because 終わるコマンドにも PTY とプロセス ID が付き、既存の承認、記録、評価のタスクをすべて作り直すことになる。

### `run_command` にバックグラウンドでの実行を足し、出力と入力のツールを加える

* Good, because 終わるコマンドの振る舞いと記録が変わらない。
* Neutral, because モデルはバックグラウンドにするかどうかを起動のたびに選ぶ。選び損ねた場合は、利用者がバックグラウンドへ移せる。

## More Information

サンドボックスの方針は [docs/linux-sandbox.md](../linux-sandbox.md)。同書は「ローカルの TCP サーバーは意図して使えない」としている。サンドボックスの中で loopback のソケットを許すかどうかと、ホストのブラウザからそのサーバーへ届かせる方法は、この ADR では決めない。届かせる方法は未検証である。
